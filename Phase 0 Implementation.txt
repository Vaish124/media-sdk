  1. Assignment Requirements (source of truth)

  Deliverables:
  - media-core — framework-agnostic Pexels client (search, curated/trending,
  pagination, single-item fetch), private API key handling, event emitter
  (view/download events, subscribe/unsubscribe, default console listener), pure
  TS, typed, error handling, basic caching/de-dupe.
  - Platform wrappers — media-react and media-native, same contract, no business
  logic, only adapt core to platform idioms. Wrappers are the only layer that
  imports media-core. Hook naming/shape/count is the candidate's choice.
  - Component libraries — media-ui-react and media-ui-native, each shipping Grid
  (infinite scroll), Lightbox (image, +video if time allows, web focus/keyboard
  handling), Reel Swiper (snap paging, active-item detection). Headless: hooks
  + prop-getters, zero shipped styles, and zero imports from core or wrappers.
  - Web app — the only place importing both media-react and media-ui-react.
  Search → Grid → Lightbox → Reels view for videos. Visual polish not scored.
  - Two SKILL.md docs — "wiring data" and "using components," proven to actually
  steer an AI tool while building the app.

  Hard constraints: strict dependency direction (app → wrappers → core, app → 
  components), core must be portable enough to power a CLI, AI-assisted parts
  must be noted in the README.

  Submission: repo link, live app URL, SDK docs URL, components docs URL, link
  to AI chat(s) used.

  2. Planned Architecture (MASTER_PROMPT)

  pnpm + Turborepo monorepo. packages/ holds the five SDK packages, apps/web is
  a Vite+React+TS app, skills/ holds the two SKILL.md files. Boundary
  enforcement is done via an ESLint import/no-restricted-paths config (Phase 0)
  rather than convention alone — core can't reach React/RN or the wrappers,
  media-ui-react/media-ui-native can't reach core or either wrapper, media-react
  can't reach the UI packages. This directly encodes the assignment's
  dependency-direction constraint as a lint rule, which is a good translation of
  a "soft" requirement into something CI-checkable.

  Data flow: app → media-react (provider+hooks) → media-core 
  (client/emitter/cache), and separately app → media-ui-react (headless hooks),
  with nothing crossing between the two branches except in app.

  4. Conflicts / Gaps Between the Two Documents

  - Biggest one: media-native and media-ui-native are listed as full 
  deliverables in ASSIGNMENT.md ("media-native — same contract, React Native
  wrapper"; "media-ui-react and media-ui-native, each shipping: Grid, Lightbox,
  Reel Swiper"), but MASTER_PROMPT Phase 3 reduces both to type-correct stubs
  that throw at runtime. This is a real scope cut relative to the literal
  deliverable list, not just an implementation-plan detail — flagged here
  because it's the kind of thing you'd want to explicitly bless before work
  starts, even though the assignment's own evaluation criteria ("sensible
  scoping under time pressure... documented") anticipates cuts like this.
  - ReelView hardcodes the search query to 'nature' instead of deriving it from
  the user's search (Phase 5). The assignment's flow description — "Search bar →
  Grid → tap opens Lightbox → a Reels-style view for video results" — reads as
  if the Reels view should reflect the active search, not a fixed term.
  MASTER_PROMPT calls this "a known simplification" in the ReelView spec itself,
  but it is not listed in the Phase 7 Scoping Decisions table that's supposed
  to be the exhaustive cut-list — that table only covers native stubs,
  video-in-lightbox, and visual polish. Worth adding to that table or
  reconsidering.
  - Minor gray area, not a hard conflict: the assignment says wrappers should
  contain "no business logic," but useMediaSearch (Phase 2) owns fairly specific
  behavior — stale-response guarding, page accumulation, and deciding when to
  emit view events. That's arguably "adapting core to React's idioms" (which is
  allowed) rather than business logic, but it's the one place the line gets
  blurry and could draw scrutiny from a reviewer applying the constraint
  strictly.
  - Everything else lines up cleanly: auth/key handling, typed contracts, event
  emitter shape, caching/de-dupe, headless prop-getter pattern, the Phase
  6-before-5 sequencing (which is explicitly designed to satisfy the
  assignment's "skills must be demonstrated steering the AI" requirement), and
  the submission checklist (repo, live URL, SDK docs, component docs, chat
  link).
